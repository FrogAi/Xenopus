# Compare behavior and performance

Use the device when hardware behavior matters, and local replay or analysis when that adequately answers the question. For A/B/C or larger comparisons, identify each actual variant, workload or route segment, settings and correctness criteria. Choose useful metrics such as response-time distributions, CPU/memory use, frame delivery, throughput or output quality according to the question.

Control material confounders: inputs, other processes, warmup, thermal/power state, caches and run order. Use repetitions and matched baseline/candidate conditions sufficient to expose variability. Capture the evidence needed to reproduce the comparison, including versions, commands, input identities, outputs and measurement limits. Check behavioral and output-quality tradeoffs alongside speed or resource savings. Use charts or aligned examples when they make the result clearer.

Distinguish source analysis, synthetic component results, replay, target-device measurements and observed vehicle behavior. Do not turn a component timing, simulated curve or static configuration into a claim about real driving, whole-system performance or safety. If representative inputs or conditions are missing, produce the feasible bounded evidence and identify what remains unmeasured.

## Measuring on the device

Measure code that runs on the device on the device; PC timings do not transfer. Before measuring, match the state the code runs in during a drive:

- **Cores:** check `/sys/devices/system/cpu/online`. On the bench, power saving can take cpu4-7 offline while the screen is off; with the screen on, all eight are online, and the difference in timings is large.
- **Onroad:** processes and paths that run only while driving need the device onroad. On the bench, set the `ForceOnroad` param with `ForceOffroad` false. A fork may read these through its own settings layer, so check how its own UI forces the drive state and do the same. Without a car, clearing it may leave the device onroad; run `touch /tmp/booted` first, as SKILL.md says, then restart `comma.service` and confirm `IsOnroad` is back to 0. Even then, card waits for CAN traffic to identify the car, so exercise car-specific logic by replaying CAN or with a harness.
- **Bench-only load:** some services behave differently without the car's conditions; athenad's reconnect loop, for example, can use substantial CPU on the bench. Note such load and account for it.
- **In a parked car:** forcing onroad does not hold off the device's own shutdown. With the engine off it still powers down on its shutdown timer (`DeviceShutdown`, counted from when the car was last really on, not from the start of the forced run), on low car-battery voltage (`LowVoltageShutdown`), or when its estimate of the car battery's remaining charge runs out, which the onroad power draw speeds up, so a forced run can end well within an hour. That loses everything held in RAM (`/tmp`, `/dev/shm`). For the first hour after a boot these rules are held off, but only while the device has not been onroad in that boot, and a forced run counts as onroad. So a device that sat idle can power off once its uptime passes an hour, and forcing onroad inside that hour removes the hold-off at once. Read the car battery voltage first (`peripheralState.voltage`, in mV; the rule compares a slow average of it with `LowVoltageShutdown`, in volts), along with those settings and how long the car has been off, keep needed evidence on `/data` or off the device, and for longer tests ask for the engine to run, which ends the forced state and makes it a real onroad run.

Take per-process numbers from `/proc`: CPU time as the change in utime plus stime in `/proc/<pid>/stat` over a fixed interval, in clock ticks (divide by `getconf CLK_TCK`, which is 100 on a comma three, for seconds), or the CPU percentage from `top -b`, resident memory from VmRSS and threads from `/proc/<pid>/status`, open files from `/proc/<pid>/fd`, and free memory from MemAvailable in `/proc/meminfo`. For loop timing, use the timestamps the process already logs or publishes.

For memory, VmRSS overstates the Python daemons: most of it is the manager's preloaded code, shared by all of them, so compare proportional size instead (sum the `Pss:` lines of `/proc/<pid>/smaps`; the comma 3X's 4.9 kernel has no `smaps_rollup`). GPU and camera buffers are largely outside process RSS: read GPU memory from `/sys/class/kgsl/kgsl/page_alloc` (total, in bytes) and, as root, `/sys/kernel/debug/kgsl/proc/<pid>/mem` (per process), and ION buffers from `/sys/kernel/debug/ion/heaps/system` and `/sys/kernel/debug/dma_buf/bufinfo`. The memory percentage openpilot reports is (MemTotal - MemAvailable) / MemTotal, so reclaimable file cache is not in it, but tmpfs (`/dev/shm`, `/tmp`) is.
