# Investigate crashes and hangs

For incidents before a reboot, inspect retained boot logs for archived `pstore` and captured journal data even when the live journal lists only the current boot. Establish boot identity and clock corrections before aligning events: wall-clock timestamps can be wrong until synchronization, and crash-report filenames can reflect collection time rather than failure time.

On AGNOS, `/cache/debug/<boot number>/pstore` keeps the kernel console of a boot that ended in a warm reboot. Order those folders by boot number, since their timestamps come from the unsynchronized boot clock. Removing power loses the hung boot's pstore; its last activity then comes from the swaglog timestamps in `/data/log` and the manager's crash logs in `/data/error_logs`. Ping answering while SSH does not suggests a userspace hang or resource exhaustion rather than a network loss. Before treating a log gap or error as a failure, match it against your own actions: a reboot you requested ends with the display server stopping first, which the UI logs as a broken Wayland connection.

To find what caused an unexpected change on the device, such as a deleted directory or a stopped service: `last` lists only interactive (terminal) SSH logins, not commands run as `ssh host command`; `~/.bash_history` is written only when a shell exits; a directory's modification time shows when an entry in it was last added, removed or renamed; and the transcripts of the Claude and other agent sessions on the PC show which commands they ran.

A missing stack in a tombstone or uploaded report does not establish that the underlying core is unusable. Check retained device crash artifacts, preserve originals, and extract into task-specific staging. Match the incident's executable and shared libraries before interpreting native stacks or private object layouts; distinguish direct core bytes from code GDB loads from current files.

Identify the actual logging destination for the failing component. Graphics-driver records may be in Android's log service rather than openpilot logs or the system journal. Verify reader coverage and retention before using an absent error as evidence. Distinguish a watchdog-triggered restart from the initiating failure. Trace material competing explanations through their required state transitions, and distinguish excluded paths from those the available evidence cannot resolve.

For heap corruption, AddressSanitizer does not work on a comma 3X: GCC's runtime, the only one installed, aborts at startup (its allocator needs an address the kernel's 39-bit address space does not have). This was not checked on a comma three; try `LD_PRELOAD=/usr/lib/aarch64-linux-gnu/libasan.so.8 /bin/ls` there first. glibc's own checks catch only some double frees: in tests on glibc 2.39 (run on a PC) an immediate repeat on the same thread aborted, while a second free from another thread, or after the memory was reused, went unreported, so a clean run rules nothing out. glibc's checking allocator (`LD_PRELOAD=libc_malloc_debug.so.0` with `GLIBC_TUNABLES=glibc.malloc.check=3`) also caught the second free from another thread in those tests, but not the free after reuse. Catching that takes a small preloaded malloc/free wrapper that keeps freed blocks in a quarantine and records the allocating and freeing call stacks (such a wrapper can catch double, cross-thread and stale frees and writes after free). To preload a library into the UI, see "Swapping in a test binary" in [execution-setup.md](execution-setup.md).
